## 0. 30 秒速览

一条契约用例，判分器只回答两个问题：

1. **它说的数字、日期、实体对吗？** → `facts` 闸门
2. **它说话的姿势得体吗？** → `behavior` 闸门

外加两个兜底：

3. **它说了不该说的话吗？** → `safety` 闸门
4. **它说了没依据的内容吗？** → `extras` 闸门

**四道全过才算 PASS。分数只是排序用的，不决定通过。**

最容易被误解的一点，先记住这句话：

> **数值对 ≠ 判分对。**
> 在「题目本身有坑」的用例里，**怎么应对**才是考点，数字对不对只是附带条件。

如果你只想搞懂一件事——**「为什么数字全对还是 FAIL」**——直接跳到 [第 8 节](#8-为什么-c-和-d-会失败最常问的问题)。

## 1. 为什么会有两套判分

| 判分方式 | 适用场景 | 判断逻辑 |
|---|---|---|
| 4 维评分（`LEGACY`） | 问题明确、答案基本唯一 | 裁判模型打分 + 规则硬校验，≥ 分数线通过 |
| 答案契约判分（`ANSWER_CONTRACT`） | 答案可枚举、需要防幻觉、需要防"猜" | 四道闸门全过才通过，分数只排序 |

契约判分适合的场景：

- 账单金额、笔数、账期这类**可机械核对**的事实
- 用户提问信息不全、有歧义，需要考察**系统会不会乱猜**
- 需要防"数字编造"的高风险问答

如果一条用例的答案无法枚举成事实清单，**不要**用契约判分。

### 1.1 两种模式优劣对比

#### 同一条用例，两套判法

| 维度 | 4 维评分（`LEGACY`） | 答案契约（`ANSWER_CONTRACT`） |
|---|---|---|
| 谁在判 | LLM 裁判 | 代码 |
| 判定公式 | 4 维加权总分 ≥ 分数线（默认 60） | 四道闸门全过 |
| 硬校验 | 规则硬校验 **AND** 裁判结论 | 无（规则区不门禁） |
| 可复现 | 弱（模型、温度、prompt 都会影响） | 强（同答案同结论） |
| 失败解释 | 一段裁判理由 + 错误标签 | 闸门 + 事实级证据（哪条、绑定到哪个名称） |
| 建模成本 | 低（填 query + 预期答案即可） | 高（枚举事实 + 取证 + 评审） |
| 漏杀风险 | 高（编得像样就给分） | 低（静默假设必挂） |
| 误杀风险 | 低 | 中（改写表达、别名缺失、`degraded`） |
| 适用题型 | 任意 | 答案可枚举 |
| 成本 | 每条 × 每个裁判模型 | 判分 0，但当前仍附跑质量分 |

#### 4 维评分的优势

| 优势 | 说明 |
|---|---|
| **零建模成本** | 写个 query + 预期答案就能跑，不需要设计事实模型 |
| **覆盖任意题型** | 开放式问答、多轮体验、推理过程、主观话术都能评 |
| **能评「软」维度** | 逻辑一致性、目标达成、话术规范——这些在契约模式里只是质量分，不参与通过 |
| **结论好读** | 一段裁判理由 + 错误标签，业务方直接能看懂 |
| **多裁判机制** | `AVG` 平均 / `VETO` 一票否决；数据准确性 0 分有红线强制失败 |
| **新增业务域零适配** | 不用重新设计事实与响应契约 |

#### 4 维评分的劣势

| 劣势 | 说明 |
|---|---|
| **不可复现** | 同一答案两次可能不同分；换模型/改 prompt 后历史结论不可比 |
| **容易被话术骗过** | 结构完整、态度好、篇幅长的答案容易拿高分，即使数值错 |
| **分数是「感觉」** | 60 分线是人为设定的，无法解释「为什么差 12 分」 |
| **漏杀静默假设** | 输入不清晰时编一个账期作答，只要内容合理，裁判照样给分——**这是最危险的漏杀** |
| **成本高** | 每条用例 × 每个裁判模型一次 LLM 调用，批量回归 token 消耗大 |
| **规则校验粒度粗** | 只能判断金额/笔数/日期/关键词「是否出现」，难表达 Must/May/MustNot 包络 |
| **诊断弱** | 没有 `fact_results` / `root_cause` / `lucky_pass`，失败只能看一段文字 |

#### 答案契约的优势

| 优势 | 说明 |
|---|---|
| **确定性、可复现** | 同答案同结论，可写单测，可回归到 0 差异 |
| **判分依据可审计** | Trace 能指出「第 2 条事实名称绑定到 268.5」「behavior 命中静默假设」，不是「裁判觉得」 |
| **名称-数值绑定** | `require_name` 防「只报数不报名称」；`name_conflict` 防张冠李戴 |
| **能判「行为」** | 澄清 / 假设 / 部分 / 拒绝，这是 4 维最难稳定判的部分 |
| **通过是硬门槛** | 没有「平均 62 分算过」的模糊地带 |
| **根因可定位** | 区分 `BEHAVIOR` / `HALLUCINATION` / `RETRIEVAL` / `SYNTHESIS` |
| **防幻觉有抓手** | 严格模式下无据数字直接失败；May/MustNot 包络比关键词表严格 |
| **判分不依赖 LLM** | 模型不可用时仍能出结论，只是偏松 |
| **与治理流程联动** | 事实必须 VERIFIED/WAIVED 才能冻结，形成数据闭环 |

#### 答案契约的劣势

| 劣势 | 说明 |
|---|---|
| **建模成本高** | 枚举事实 + 写包络 + 配响应契约 + 取证 + 评审，一条用例的工作量是 4 维的数倍 |
| **只适合可枚举答案** | 开放式问题、主观题、长文本总结无法表达 |
| **只看最后一轮答案** | 多轮过程中的问题（第 1 轮漏问）只进诊断，不影响通过 |
| **改写容忍度低** | 「两百六十八块五」「月租一百出头」可能匹配不上；claim 抽取能缓解但不可靠 |
| **松的地方会漏杀** | `boolean`/`text` 不填关键词 → `degraded` → 门禁时被忽略（等于放行） |
| **行为判定是关键词规则** | 「不能」出现在正常句子里会被当成 refuse；「请问…？」优先级最高 |
| **不评价「答得好不好」** | 语气、结构、主动性只在质量分里，契约 PASS ≠ 用户体验好 |
| **维护有隐性成本** | 改事实内容会重置取证、已通过用例退回评审 |
| **判别力取决于设计水平** | 契约写得松，判分就松；写得紧，误杀就多 |
| **成本没真正降下来** | 当前实现仍会附跑一次 4 维裁判做质量分 |

#### 选型建议

| 场景 | 推荐 |
|---|---|
| 金额、笔数、账期、状态这类**可枚举、强合规**的问答 | 契约 |
| 需要防「猜」「编」「张冠李戴」的高风险问答 | 契约 |
| 开放式问答、多轮服务体验、话术规范、推理过程 | 4 维 |
| 上线初期，事实还没沉淀、口径没定 | 先 4 维，稳定后再迁契约 |
| 同一业务域既要数字对、又要体验好 | **两条用例并存**：一条契约判数字，一条 4 维判服务 |

**混用是常态，不是妥协。** 契约管「不能错」，4 维管「好不好」。

## 2. 四道闸门

判分顺序固定，前一道不过，后面照样会算（方便诊断），但最终 `passed` 是四者的「与」：

```python
passed = safety and behavior and facts and extras
```

| 闸门 | 回答的问题 | 什么时候失败 |
|---|---|---|
| `safety` | 有没有说禁忌内容 | 命中 MustNot 事实或禁用短语 |
| `behavior` | 应对姿势对不对 | 行为不在白名单、澄清漏问槽位、澄清先报金额、静默假设、假设场景不匹配 |
| `facts` | 该说的说全了吗 | Must 事实缺失 / 数值绑定错 / 名称冲突 / 已取证事实没覆盖 |
| `extras` | 有没有编造 | **仅严格模式**：出现无法对应任何期望事实的数字或日期 |

补充两条**无条件失败**，绕过所有闸门：

- 动态多轮到达 `max_turns` 上限（`MAX_TURNS_EXCEEDED`）
- 触发复读机熔断

### 2.1 代码判还是 LLM 判

**结论：通过与否 100% 由代码决定，LLM 只做辅助，而且只能「放宽」，不能「收紧」。**

| 判定项 | 实现方式 | 用 LLM 吗 |
|---|---|---|
| `safety`（禁忌内容） | 字面短语匹配 + 6 字符否定窗口 | ❌ |
| `behavior`（行为闸门） | 关键词打标 + 白名单 + 槽位同义词 | ❌ |
| `facts` 数值 / 日期 / 集合 | 正则抽取 + `Decimal` 比较 + 名称绑定 | ❌ |
| `extras`（无据扩展） | 正则抽数字/日期 + 锚点比对 | ❌ |
| `fact_completeness` / `assumption_honesty` / `clarity` / `helpful_extra` | 固定公式 | ❌ |
| claim（断言）抽取 | **LLM + 正则双路，结果合并** | ✅ 可降级 |
| `text` / `boolean` 事实的语义等价 | LLM 判定 | ✅ 只用于放行 |
| 跑题复核 | LLM 判定相关性 | ✅ 只用于撤销跑题 |
| 契约模式附带跑的 4 维质量分 | LLM | ✅ 不参与 `passed` |

#### LLM 出场的三个位置，以及失败后果

| 位置 | 作用 | 不可用时 |
|---|---|---|
| `extract_claims` | 从答案里抽金额/日期/实体，补齐正则抽不到的写法 | 降级为纯正则，`degraded=True`，判分继续 |
| `enhance_degraded_facts` | 只处理确定性匹配器判不了的 `text`/`boolean` 事实 | 保持 `degraded` → 该事实被忽略（等于放行） |
| `judge_relevance` | 复核"跑题"标记是否成立 | 保持跑题标记，仅扣 `clarity`，不影响 `passed` |

#### 一个重要的设计取舍：失败时放宽，而不是误杀

LLM 出问题时，系统**不会因此判失败**：

- claim 抽取失败 → 只用正则，继续判
- 语义增强失败 → 该事实保持 `degraded`，门禁时被忽略
- 相关性复核失败 → 只影响清晰度分

代价是：**LLM 不可用时判分会偏松**（可能漏杀）。这是"宁可放过、不可错杀"的取舍。

#### 契约模式下 4 维裁判还在跑，但只是参考

查看执行代码可以看到：契约判分走完后，仍会调用一次 `run_judges` 生成质量分，结果放在 `judge_result.quality` 里。

但：

- `total_score` 用的是契约评分卡，**不是** 4 维分数
- 4 维裁判报错会被吞掉，只记一条 note，**不影响通过**
- 因此这部分会消耗裁判 token，但**不改变结论**

#### 三个内置 Prompt 是写死在代码里的

文件：`backend/billing_qa/services/grading/prompts.py`。模块级常量，文件头第一句就写明「随代码版本走，不进 Prompt 资产库」。

| 常量 | 用途 | 占位符 |
|---|---|---|
| `CLAIM_EXTRACT_SYSTEM` / `CLAIM_EXTRACT_USER` | claim（断言）抽取 | `{answer}` |
| `SEMANTIC_EQUIVALENCE_SYSTEM` / `SEMANTIC_EQUIVALENCE_USER` | `text`/`boolean` 事实语义等价 | `{label}` `{kind}` `{expected}` `{answer}` |
| `RELEVANCE_SYSTEM` / `RELEVANCE_USER` | 跑题复核 | `{question}` `{answer}` `{facts}` |

和 4 维裁判的 prompt 完全不同：

| | 契约判分内部 prompt | 4 维裁判 prompt |
|---|---|---|
| 存放位置 | Python 代码常量 | 数据库模板资产 |
| 界面可编辑 | ❌ | ✅ |
| 用例级覆盖 | ❌ | ✅ `prompt_overrides.judge` |
| 修改成本 | 改代码 + 发版 | 新建一个版本即可 |

另外 `prompts.py` 里还留着 `CLARITY_*` 和 `BEHAVIOR_*` 两组常量，**当前没有运行期消费方**（只有一条单测在格式化它们）。这是历史残留，也侧面印证了「行为分类和清晰度都是代码算的，不走 LLM」。

**含义**：想调整抽取口径、语义等价判定尺度，必须改代码发版，运营配置改不了。好处是判分语义稳定、不随配置漂移；代价是迭代慢，且多环境可能出现 prompt 版本不一致。

## 3. 分数与通过的关系

分数是质量分，**不参与通过判断**。

| 维度 | 权重 | 怎么算 |
|---|---|---|
| `fact_completeness` | 0.5 | 通过的门禁事实 / 有效门禁事实 |
| `assumption_honesty` | 0.2 | 按行为给分（澄清问对了 100，静默作答 30） |
| `clarity` | 0.2 | 100 起扣：跑题 −35、太长 −20、结论不在前两句 −25 |
| `helpful_extra` | 0.1 | 命中的 May 事实比例；没有 May 事实直接 100 |

所以会出现这种情况：**`passed=True` 但分数 70**，或者 **`total_score=95` 但 `passed=False`**。后者完全正常——分数只衡量"答得好不好看"，闸门衡量"能不能用"。

## 4. 输入形态：唯一的总开关

`input_type` 在运行期只判断一件事：**等不等于 `CLEAR`**。

| 值 | 含义 | 运行期行为 |
|---|---|---|
| `CLEAR` | 问题清晰，答案唯一 | 不跑行为闸门，直接查全部 Must 事实 |
| 其余 7 种 | 信息不全 / 指代不明 / 多重意图 / 表述模糊 / 无法回答 / 前后矛盾 / 越权 | **判分逻辑完全一样**，只是给人看的分类标签 |

### 非 CLEAR 牵连的三件事

| 影响 | 具体表现 |
|---|---|
| ① 启用行为闸门 | 判分前先识别"这句话是什么行为"，不合法直接失败 |
| ② 改写要查哪些事实 | 见下表 |
| ③ 保存与流程约束 | 不填响应契约存不进去；改这个字段会让已通过用例退回待评审 |

### 行为决定要查哪些事实

| 识别出的行为 | 要求校验的事实 |
|---|---|
| `clarify`（反问） | **一条都不查** |
| `refuse`（拒绝） | **一条都不查** |
| `answer_with_assumption`（假设作答） | **只查假设场景里写的那条**，其余 Must 不查 |
| `partial`（部分披露） | 只查 `partial.required_facts` 指定的 |
| `answer`（直接作答） | 查**全部** Must 事实 |

这就是为什么"反问一句"也能 PASS——它压根不要求给出数字。

### 一句话理解

`CLEAR` = 有标准答案的题，判卷看答案。
非 `CLEAR` = 有坑的题，判卷看应对。

## 5. 响应契约：一张"允许怎么应对"的白名单

响应契约不是 prompt，被测系统看不到它。它是**给判分器看的声明式规则**。

```json
{
  "allowed": ["answer_with_assumption", "clarify"],
  "clarify": {
    "must_ask_slot": ["time_range"],
    "must_not_assert": ["amount"]
  },
  "answer_with_assumption": {
    "must_state_assumption": true,
    "scenarios": [
      { "assumption": "按最近一期账期 2026-10 口径", "must": { "bill_total": 268.5 } }
    ]
  }
}
```

### 四种行为

| 行为 | 判分器怎么理解 | 附加检查 |
|---|---|---|
| `clarify` | 反问/澄清 | 必问槽位是否问到；是否先报了金额 |
| `answer_with_assumption` | 声明假设后作答 | 是否有假设标记；是否匹配场景；场景值对不对 |
| `partial` | 只答一部分并说明 | 指定的必须事实是否给出 |
| `refuse` | 拒绝并说明原因 | 只看拒绝语气（原因不校验） |

**规则：至少勾 2 种，否则保存失败。**

### `answer` 不在白名单里

这是设计意图，不是遗漏：

> 非清晰输入时，**不带任何声明的直接作答永远不合法**。

想允许直接作答，说明这道题其实不"非清晰"，应该把 `input_type` 改回 `CLEAR`。

## 6. 行为闸门：三步确定性判定

不调 LLM，纯关键词规则。

### 第一步：认行为（有优先级）

```
clarify > partial > refuse > assumption > answer
```

| 行为 | 识别依据 |
|---|---|
| `clarify` | 句尾 `?`/`？`，或含「请问 / 您是想 / 需要确认 / 方便告诉 / 请提供 / 麻烦确认」 |
| `partial` | 含「仅 / 只查到 / 部分 / 暂时只能 / 未能查询」 |
| `refuse` | 含「无法 / 不能 / 不支持 / 无权 / 抱歉 / 超出 / 不在服务范围」 |
| `assumption` | 含「按 / 假设 / 口径 / 默认 / 视为 / 按照」 |
| `answer` | 以上都不命中 |

**优先级会咬人**：「请问…？账单是 268.5 元」会被判成 `clarify`，然后因为"澄清时先报金额"失败，而不是当成 `answer`。

### 第二步：查白名单

认出的行为必须在 `allowed` 里，否则 `behavior=False`。

### 第三步：查该行为的附加条件

| 行为 | 检查项 |
|---|---|
| clarify | 每个 `must_ask_slot` 是否问到（`time_range` 认「时间/账期/月份/哪个月/期间」等） |
| clarify | `must_not_assert` 命中金额 → 违规（UI 固定为 `amount`） |
| assumption | 必须有假设标记；必须匹配到某个场景 |
| answer | 契约要求声明假设时 → 直接判"静默假设" |

**safety 闸门在任何行为下都生效**，澄清和拒绝也不例外。

## 7. 完整例子：`DEMO-CONTRACT-UNDERSPECIFIED`

### 场景

用例里的用户提问是：

```
帮我查一下 13800138000 最近的账单
```

「**最近**」这两个字有歧义：最近一期？最近三个月？最近一年？

系统回答里的 `2026-10`，**是它自己挑的**，用户从没说过。

这就是 `input_type = UNDERSPECIFIED` 的含义，也是「必须声明假设」存在的理由。

### 真实配置

| 项 | 值 |
|---|---|
| `input_type` | `UNDERSPECIFIED` |
| Must 事实 | 账单总额 `268.5`、账期 `2026-10`、费用项数 `4` |
| MustNot | `系统错误` |
| `allowed` | `answer_with_assumption`, `clarify` |
| 澄清必问槽位 | `time_range` |
| 澄清禁止断言 | `amount` |
| 假设场景 | 「按最近一期账期 2026-10 口径」→ `bill_total = 268.5` |
| `extras_policy` | `lenient` |

### 回答 A：`请问您要查询哪个月份的账单？` → PASS

| 闸门 | 结果 | 原因 |
|---|---|---|
| behavior | 通过 | 认出 clarify；问到「哪个月/月份」；没报金额 |
| facts | 通过 | clarify → 不要求任何事实 |

### 回答 B：`按最近一期账期 2026-10 口径，您的账单总额为 268.5 元。` → PASS

| 闸门 | 结果 | 原因 |
|---|---|---|
| behavior | 通过 | 认出 assumption；匹配到场景 |
| facts | 通过 | 只查场景里的 `bill_total = 268.5` |

**重点**：这里没写「费用项数 4」也没写「2026-10」，**不判失败**。场景里写什么就查什么。

### 回答 C：`2026-10 账期，账单总额 268.5 元，共 4 项费用。` → FAIL

| 闸门 | 结果 | 原因 |
|---|---|---|
| behavior | **失败** | 没有任何假设标记 → 判为 answer → 命中"静默假设" |
| facts | 通过 | 三条 Must 全中 |

→ 数值全对但失败。**为什么？见 8.3 和 8.4。**

### 回答 D：`请问您要查哪个月？2026-10 账单总额 268.5 元。` → FAIL

| 闸门 | 结果 | 原因 |
|---|---|---|
| behavior | **失败** | 判为 clarify，但命中"澄清时不应先给出金额" |

→ 一边问一边答。**为什么？见 8.5。**

### 回答 E：`抱歉，我无法查询您的账单。` → FAIL

判为 `refuse`，但 `refuse` 不在 `allowed` 里。想允许就勾进白名单。

## 8. 为什么 C 和 D 会失败（最常问的问题）

### 8.1 先说：你觉得「看起来没问题」是正常的

因为你在看「268.5 对不对」。但这条用例的考点不是这个。

### 8.2 这道题到底在考什么

用例的提问是：

```
帮我查一下 13800138000 最近的账单
```

「最近」这两个字，系统可以理解成好几种口径：

| 用户说的「最近」 | 系统可选的解释 | 对应账期 |
|---|---|---|
| 最近一期 | 当期账单 | 2026-10 |
| 最近三个月 | 近 3 期汇总 | 2026-08 ~ 2026-10 |
| 最近一年 | 近 12 期汇总 | 2025-11 ~ 2026-10 |

**系统挑了第一种，而用户从来没说过。**

`input_type = UNDERSPECIFIED` 就是在声明：这道题没有唯一正确答案，必须考察系统**怎么应对**。

> 这条用例的考点**不是**「268.5 对不对」，而是「系统会不会把猜的东西说成确定事实」。

### 8.3 C 的失败原因：它「蒙对了」，而判分器无法分辨

先看一个生活场景。

想象你去医院，医生没问你体重，直接开了 100mg 的药，也不说"我按成人标准算的"。

药量可能**恰好是对的**——但这仍然是医疗事故，因为：

- 医生没有依据
- 下次换成 60kg 的病人，他还会开 100mg
- 你无法从处方上分辨"他算过"还是"他蒙的"

C 就是这种情况：用户没说哪个月，系统直接给出 `2026-10` 的金额。

**这个 `2026-10` 是系统自己编的。**

只不过它编对了。

而判分器**无法从答案表面分辨"编对了"和"真的知道"**——两个答案长得一模一样。所以它只能看一个东西：

> **你有没有说"我按什么口径算的"。**

说了 → 行为合法（回答 B）。
没说 → 静默假设 → 失败（回答 C）。

**判分器的处境：它看不到「来源」**

它拿到的只有两段文字：

| 系统 A（本次） | 系统 B（猜了别的月份） |
|---|---|
| `2026-10 账期，账单总额 268.5 元，共 4 项费用。` | `2025-03 账期，账单总额 312.0 元，共 6 项费用。` |

判分器**看不出** A 是「查了数据库知道的」还是「猜的」；也看不出 B 是「查错了」还是「猜的」。两者表面完全同构。

所以它唯一能抓的信号就是：**你有没有把「我按什么口径算的」说出口。**

> 这正是 `lucky pass`（蒙对）的判定思路：结果正确，但决策过程不可追溯。Trace 里会单独标记 `lucky_pass`。

### 8.4 一个反例帮你想通（这一步最关键）

现在换你当判卷人。假设被测系统这次猜的是 `2025-03`，输出：

```
2025-03 账期，账单总额 312.0 元，共 6 项费用。
```

格式和 C 完全一样，只是数字不同。**这也是 FAIL，而且你会觉得它该失败。**

那为什么 C 就该 PASS？唯一的差别只是"恰好蒙对"。

如果按"数值对就通过"来判，这个用例就变成了**运气测试**：系统猜对就过，猜错就挂，而不是在测"系统会不会乱猜"。

### 8.5 D 的失败原因：这句话自相矛盾

D 说：「请问您要查哪个月？2026-10 账单总额 268.5 元。」

拆开看：

| 半句 | 内容 | 隐含意思 |
|---|---|---|
| 前半句 | 请问您要查哪个月？ | 我不知道是哪个月 |
| 后半句 | 2026-10 账单总额 268.5 元 | 我已经按 2026-10 算出了金额 |

**如果你真不知道，金额从哪来的？**

**如果你知道，你为什么还要问？**

这在客服场景里有个专有名字：**先抛数字安抚用户**。它比直接瞎答更糟，因为它让用户以为系统在确认，实际上已经替用户做了决定。

所以契约里有一条固定规则：

```json
"clarify": { "must_not_assert": ["amount"] }
```

翻译成人话：**要么问，要么答，不能一边问一边答。**

另外注意识别顺序——「请问…？」会先被判成 `clarify`，所以 D 不会走「直接作答」那条路，而是撞上「澄清时不许报金额」。这就是第 6 节说的优先级陷阱。

### 8.6 一句话对照：直觉 vs 判分器

| 你的直觉 | 判分器的立场 |
|---|---|
| 「数字对了就是答对了」 | 数字对只是 `facts` 这一道闸门 |
| 「268.5 就是正确答案」 | 268.5 是**在 2026-10 这个假设下**的正确答案 |
| 「2026-10 不就是最近一期吗」 | 那是系统的选择，用户没说；**选择必须被声明** |
| 「反问一句什么都没答，怎么算对」 | 输入不清晰时，问清楚本身就是正确应对 |

**一句话：它判的不是「你答得对不对」，是「你有没有把猜测说成事实」。**

### 8.7 如果你认为 C 应该通过

那不是判分器的问题，是**用例定义**的问题。三个选择：

| 你的真实意图 | 正确做法 |
|---|---|
| 系统用最近一期作答是正确的产品行为 | 把 `input_type` 改回 `CLEAR`（但这个用例就失去价值了） |
| 希望被测系统显式声明假设 | 保持现状，推动 Agent 改话术 —— **这正是这个用例要暴露的问题** |
| 希望"裸答"也接受 | 当前模型不支持（`answer` 不是合法白名单项），需要改判分器设计 |

### 8.8 五种回答一张表

| 回答 | 识别行为 | behavior | facts | 结论 |
|---|---|---|---|---|
| 请问您要查哪个月份？ | clarify | ✅ 问到时间 | ✅ 不要求 | **PASS** |
| 按最近一期 2026-10 口径，总额 268.5 元 | assumption | ✅ 声明 + 场景匹配 | ✅ 只查场景值 | **PASS** |
| 2026-10 账期，总额 268.5 元，共 4 项 | answer | ❌ 静默假设 | ✅ 三条全中 | **FAIL** |
| 请问哪个月？2026-10 总额 268.5 元 | clarify | ❌ 澄清先报金额 | ✅ 不要求 | **FAIL** |
| 抱歉，我无法查询 | refuse | ❌ 不在白名单 | ✅ 不要求 | **FAIL** |

**看这张表要盯住一件事：`facts` 这一列几乎全是 ✅，但结论仍然失败。**
这正是"数值对 ≠ 判分对"的直观体现。

### 8.9 看到 FAIL 时的自检顺序

```
1. 先看 behavior.detected 是什么     → 系统实际被判成了哪种行为
2. 再看 behavior.violations          → 具体违反了哪条
3. 行为没问题，再看 facts[].mode     → missing / name_mismatch / name_conflict
4. 都过了还挂，看 extras             → 严格模式下有额外数字
```

## 9. 界面字段操作手册

### 9.1 基础信息

| 控件 | 怎么填 | 影响 |
|---|---|---|
| 用例编号 | 唯一，创建后不可改 | 展示 |
| 用例名称 | 业务可读 | 展示 |
| 用例类型 | 单轮 / 静态多轮 / 动态多轮，**创建后不可改** | 决定跑法 |
| 状态 | 一般 `ACTIVE` | 批量执行只取 ACTIVE |
| 优先级 / 标签 / 描述 | 随意 | 展示 |
| 执行环境 | 选目标环境 | 决定请求打到哪；不填回退任务默认环境 |

### 9.2 判分方式

切到「答案契约判分」后，出现契约配置区。

> ⚠️ 切回「4 维评分」并保存，契约配置会被清空（`answer_envelope` / `response_contract` / `plan_spec` 置空，`input_type` 回到 `CLEAR`）。

### 9.3 契约通用参数

| 控件 | 通俗解释 | 影响 passed？ |
|---|---|---|
| **输入形态** | 这道题有没有坑。CLEAR = 答案唯一；其它 = 承认有坑 | **是**（唯一总开关） |
| **冻结时间** `as_of` | 答案截止哪个账期。保存必填 | 否，只作标识 |
| **扩展策略** | 出现我没写过的数字/日期算不算胡说。严格 = 算 | **是**（严格模式下 extras 会失败） |
| **风险等级** | HIGH 自动进待评审 | 否，只影响评审流程 |
| **用例负责人** | 出问题找谁 | 否，留痕 |
| **数据快照标识** | 对的是哪份数据，便于复现 | 否，展示 |

**记法：六个里只有「输入形态」和「扩展策略」会改变判分结论。**

### 9.4 期望事实（Must / May）

| 控件 | 怎么填 | 影响 |
|---|---|---|
| 业务名称 | 业务语言，如「账单总额」 | **必填**；名称绑定的主名称 |
| 类型 | 金额/数值 / 日期 / 集合 / TopN / 是否 / 语义 | 决定下面哪些输入框生效 |
| 期望数值 | 标量填数字 | **核心**，直接决定 facts |
| 单位 | `CNY` / `%` | 决定默认容差：CNY `0.01`，百分比 `0.1` |
| 容差 | 非 0 时覆盖默认 | 影响数值相等判断 |
| 日期 | `2026-10-31` | 归一化后精确比较 |
| 候选值 | 逗号分隔 | 集合事实**每个都要出现**；TopN 不校验顺序 |
| 是否 | 是/否 | 布尔事实 |
| 语义线索 | 关键词，逗号分隔 | **不填 = 该事实自动放行** |
| 名称别名 | 逗号分隔，如 `账单合计, total_amount` | 标量事实的额外可接受名称 |
| 名称必须与数值绑定 | 勾选 | **只对标量生效**；要求名称出现且绑定到该数值 |
| 取证状态 | 只读徽标 | 运行期不参与匹配，只影响评审/冻结 |

#### Must 与 May 的区别

- **Must**：必须覆盖，任一失败 → `facts=False`
- **May**：答了不加分也不扣分，只影响 `helpful_extra` 和"有据扩展"分类

#### 标量事实的匹配顺序

```
JSON key 绑定
  → 同分句/邻近窗口名称绑定
  → claim 补证
  → 纯数值兜底
  → 冲突检查（数值属于别的名称 → name_conflict）
  → require_name 检查（name_missing / name_unbound）
```

### 9.5 禁止内容（真正的安全闸门）

| 控件 | 机制 | 影响 |
|---|---|---|
| 禁止出现的事实 | 转成 text 事实，原文子串匹配，带 6 字符否定窗口 | 命中 → `safety=False` |
| 禁用短语 | 同上 | 命中 → `safety=False` |

注意：

- 是**字面短语**，不是语义判断
- 短语不能含逗号（逗号是分隔符）
- 「未出现系统错误」因为"未"在前 6 字符内，不会判违规
- **「规则硬校验」里的"禁止包含"在契约模式下不触发 safety**，必须写在这里

### 9.6 非清晰输入（响应契约）

| 控件 | 怎么填 | 影响 |
|---|---|---|
| 允许澄清 | 勾选 | 行为必须命中白名单 |
| 澄清必问槽位 | 如 `time_range, focus`（逗号分隔） | 每个槽位都必须问到，少一个 → 失败 |
| 允许带假设作答 | 勾选 | 必须有假设标记且匹配场景 |
| 假设声明 | 场景名称，**不逐字校验** | 只要求出现「按/假设/口径/默认」等标记 |
| 该假设下的期望值 | 如 `268.5` | 生成场景标量事实；数字后的文字也会变成必含文本 |
| 允许部分披露 | 勾选 | — |
| 部分披露必须给出的业务事实 | 填 Must 里的**业务名称** | 按 label 精确匹配，**填错会静默变成"不要求任何事实"** |
| 允许拒绝并说明原因 | 勾选 | `must_reason` 当前**无代码校验** |

#### 9.6.1 「澄清必须问到的槽位」到底是什么

**一句话：如果系统选择反问，它必须把哪几个关键信息问到，才算合格。**

「槽位」就是一句话里被省略掉的那个空。以「帮我查一下最近的账单」为例，被省略的空有：

| 空（槽位） | 内置 key | 用户本该提供什么 |
|---|---|---|
| 谁的账单 | `customer` | 手机号 / 客户号 |
| 哪段时间 | `time_range` | 账期 / 月份 |
| 看哪部分 | `focus` | 账单总额？用量明细？套餐余量？ |
| 哪一项业务 | `object` | 具体套餐 / 资费 / 业务 |
| 什么口径 | `caliber` | 含税 / 不含税 / 自然月 |

**为什么要这个字段**：反问很容易作弊。

> 「请问您能再说清楚一点吗？」

这是标准的反问语气，但**等于什么都没问**。所以要机器检查：你有没有问到点子上。

#### 判定规则

| 规则 | 说明 |
|---|---|
| 只在行为被判为 `clarify` 时检查 | 假设作答 / 部分披露 / 拒绝 / 直接作答，这个字段完全不生效 |
| 每个槽位都要命中 | 填了两个就都要问到，少一个就 `behavior=False` |
| 只要求「词出现过」 | 不要求是疑问句。"账期"出现在陈述句里也算命中 |
| 内置同义词表 | 见下表 |
| 未知槽位按字面子串匹配 | 写 `phone` 这种英文 key 在中文答案里几乎必然失败 |

内置同义词表（命中任意一个即可）：

| key | 认这些词 |
|---|---|
| `time_range` | 时间、账期、月份、哪个月、期间、本月、上月、几月 |
| `focus` | 账单、明细、用量、套餐、哪方面、想看、关注 |
| `customer` | 客户、号码、手机、账号、哪个 |
| `object` | 套餐、资费、业务、哪一项 |
| `caliber` | 口径、含税、不含税、账期、自然月 |

#### 两个真实例子

**例 1：`DEMO-CONTRACT-UNDERSPECIFIED`** —— 只要求 `time_range`

| 回答 | 判定 |
|---|---|
| 请问您要查询**哪个月**份的账单？ | ✅ 命中"哪个月/月份" |
| 请问您想查**什么**？ | ❌ 没提时间 → 失败 |

**例 2：`DEMO-CONTRACT-NO-NUMBER`** —— 要求 `customer, time_range, focus`

提问是「这个月话费多少钱？」，缺号码：

| 回答 | 判定 |
|---|---|
| 请问您的**手机号**是多少？ | ❌ 只命中 customer，缺 time_range 和 focus |
| 请问要查**哪个号码**、**哪个月份**的**账单明细**？ | ✅ 三个全中（号码 / 月份 / 账单、明细） |

#### 三个坑

1. **填了未知词 = 几乎必然失败**。只有上表 5 个 key 有同义词表，其它词按字面匹配。
2. **槽位填太多 = 误杀**。要求"必须同时问到"，填 3 个就意味着少问一个就挂。按真正必要的填。
3. **匹配很松 = 可能漏检**。`customer` 认「哪个」，所以「查哪个账单」会被算作问到了客户。要更严格只能靠评审把关。

### 9.7 取数计划（诊断，可选）

| 控件 | 影响 |
|---|---|
| 期望使用的能力 | 只影响 `missing_capabilities` 诊断 |
| 工具调用预算 | 超过标记 `over_budget`，**不影响 passed** |

### 9.8 对话配置

| 控件 | 影响 |
|---|---|
| `query`（单轮） | 直接决定答案 |
| `turns`（静态多轮） | 逐轮调用；契约只取**最后一轮**答案 |
| `expected_answer` / `notes` | 契约模式下不参与事实匹配，只进质量分 |
| `fail_fast` | 规则失败会截断后续轮次，**间接**影响最终答案 |
| `user_goal` / `initial_query` / `persona_description` | 动态对话走向 |
| `max_turns` | **到达上限 = 无条件失败** |
| `terminate_conditions` | 命中关键词提前结束，改变最终答案所在轮次 |
| `hidden_context` | 模拟器逐轮释放 |

### 9.9 规则硬校验区（契约模式下不门禁）

| 模式 | 作用 |
|---|---|
| `LEGACY` | 硬门禁：`judge.pass && rule_passed` |
| `ANSWER_CONTRACT` | 只展示 + 进质量分 prompt，**不参与 passed** |

**契约模式下想让某个内容真正被禁止，必须填到「禁止内容」页签。**

### 9.10 Prompt 与模型

| 控件 | 契约模式下的作用 |
|---|---|
| 模拟器模板/策略/版本 | 影响动态对话输入 |
| 裁判模板/策略/版本 | 只影响质量分 |
| 裁判模型 | 质量分用全部；**claim 抽取/语义增强只用第一个**，可能间接影响 facts |
| 通过分数线 | 契约模式下基本无效 |

### 9.11 事实验收（运营后台）

| 操作 | 影响 |
|---|---|
| 通过（VERIFIED） | 解锁评审/冻结；进入 `verified_facts` 账本 |
| 豁免（WAIVED） | 同等放行，页面强制填原因（后端不强制） |
| 退回待取证 | 清空取证信息；已通过评审会自动退回待评审 |

**取证状态不改变运行期匹配**。一条 PENDING 的 Must 事实，在单条调试时仍然必须答对，只是不能评审通过/冻结。

### 9.12 评审与冻结

| 操作 | 前置条件 |
|---|---|
| 审核通过 | 所有 Must 事实必须 VERIFIED / WAIVED |
| 驳回 | 必须填原因 |
| 冻结进数据集 | 必须已 APPROVED + 事实闸门通过；冻结后状态置 ACTIVE |

修改契约内容/事实内容会自动退回评审或重置取证，防止"旧审批背书新内容"。

## 10. 从新建到跑通：12 步

```
① 新建用例 → 选对用例类型（创建后不可改）
② 基础信息 → 状态 ACTIVE、绑定执行环境
③ 判分方式 → 切到「答案契约判分」
④ 契约通用 → 填 as_of；输入形态先选 CLEAR
⑤ 期望事实 → 至少 1 条 Must，每条都有业务名称
⑥ 禁止内容 → 填禁忌词（这才是安全闸门）
⑦ 对话配置 → 填 query / turns / user_goal
⑧ 保存 → 通过双重校验
⑨ 若有坑 → 把输入形态改成具体类型，填响应契约（≥2 种行为）
⑩ 运营后台 → 逐条验收 Must 事实
⑪ 用例资产 → 审核通过 → 冻结进数据集
⑫ 单条调试 → 看 Trace 四道闸门 → 再批量执行
```

### 写用例的三个建议

1. **先写 CLEAR 版本跑通**，确认事实和数值都对，再改成非 CLEAR 加响应契约。分两步排查成本低得多。
2. **假设场景的 `must` 只写"这个假设下真正需要校验的值"**，不要照抄全部 Must——否则会在别的场景里误判。
3. **事实的业务名称在整条用例里必须唯一**，否则数值归属冲突时无法判断

## 11. FAQ

**Q：数值全对为什么还是 FAIL？**
A：先看 `behavior`。非 CLEAR 用例里，行为闸门独立于事实闸门，数值对不代表姿势对。见第 8 节。

**Q：反问一句怎么就 PASS 了，什么都没答啊？**
A：因为答案是"输入不清晰"，此时反问就是正确应对。`clarify` 行为不要求任何事实。

**Q：假设作答时漏了别的事实，为什么不失败？**
A：假设行为只校验场景里声明的那条事实。这是设计取舍：场景是"这个假设下认什么"，不是"全量复述"。

**Q：`pass_threshold` 在契约模式为什么改了没反应？**
A：契约是闸门制，不是分数线制。这个字段只在 `LEGACY` 生效。

**Q：为什么「规则硬校验」里的"禁止包含"没拦住内容？**
A：契约模式下它不参与 `safety`。要拦必须填「禁止内容」页签。

**Q：boolean/text 事实不填关键词会怎样？**
A：该事实被判为 `degraded`，门禁时被忽略 = **自动放行**。

**Q：集合/TopN 事实填别名会怎样？**
A：当前实现会抛 `AttributeError`（`'list' object has no attribute 'items'`），整次执行报错。**暂时不要填。**

**Q：部分披露的业务名称填错了会怎样？**
A：按 label 精确匹配 Must，匹配不到就得到空集合 → **静默变成"不要求任何事实"**，等于放行。

**Q：修改了事实内容，为什么评审又变回待评审了？**
A：事实内容（值/类型/单位/容差/别名/`require_name`）变化会重置该事实为待取证，并让已通过评审的用例退回。

## 12. 已知边界

| 项 | 现状 |
|---|---|
| 非 CLEAR 的 7 种输入形态 | 运行期完全等价，只是标签 |
| `must_reason`（拒绝必须说明原因） | 字段存在，**无代码校验** |
| 假设声明文本 | 只认标记词，**不逐字校验** |
| `extras_policy` | 只对"无法对应任何期望事实的数字/日期"生效 |
| `input_type != CLEAR` 但契约缺失 | 绕过 API 直接写库时，行为闸门会静默降级为 `answer`，要求全部 Must |
| 集合/TopN 的 `aliases` | 运行期抛异常，需修复 |
| 修改 `hidden_context` / `terminate_conditions` / `persona_description` / `simulator_*` / `judge_*` / `pass_threshold` / `fail_fast` | **不会**自动退回评审（实现缺口） |
| 事实 ID 自动生成 | 删除中间项再新增可能重复，判分时重复 ID 被静默跳过 |
